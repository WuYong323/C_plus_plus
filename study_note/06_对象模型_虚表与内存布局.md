## 精炼段

虚函数的"魔法"没有任何运行时魔法——它是一张表：每个**多态类**（有虚函数的类）在只读内存里有一张**虚表 vtable**（函数指针数组，按虚函数声明顺序排布），每个**对象**开头藏一个 8 字节的**虚表指针 vptr** 指向它。调用 `p->draw()` 就是：取 `p` 的 vptr → 按编译期已知的槽位下标取函数指针 → 间接跳转，**两次额外寻址**。这和你 Cool 编译器里「对象 tag → class_meta → vtable → 函数指针」是同一个机制（C++ 少一跳：vptr 直接指向 vtable）。非多态类没有 vptr（所以加第一个 virtual 会让对象 +8 字节）。多继承会有多个 vptr 和 this 指针调整，虚继承用 vbase 指针共享基类。RTTI（`typeid`/`dynamic_cast`）也藏在 vtable 里。

## 0. 一句话直觉

> 编译器不知道 `p->draw()` 里 `p` 运行时到底是圆还是方，怎么办？它**不做决定，改查表**：让每个对象身上带一张"名片"（vptr），名片指向"这个类的能力清单"（vtable，一串函数指针）。调用时**不看你是谁，只看你的名片上第几个格子写着谁**。你 Cool 编译器里亲手生成的那张分发表，就是这个名片——只是 C++ 由编译器自动帮你生成。

## 1. 加一个 virtual，对象多了 8 字节

先做一个最直观的实验（demo 里有可跑版本）：

```cpp
struct Plain { int x; };                    // 无虚函数
struct Poly  { virtual void f() {} };       // 有虚函数

std::cout << sizeof(Plain) << "\n";   // 4（只有一个 int）
std::cout << sizeof(Poly)  << "\n";   // 8（一个 int 都没有，却是 8！）
```

**结论**：一个没有任何数据成员、但有一个虚函数的类，`sizeof` 是 8（x64）。那 8 字节就是 **vptr**——指向虚表的指针。它是编译器偷偷塞进对象头部的隐藏成员。

> **关键推论**：虚函数不是免费的。每个多态对象多 8 字节；且 vptr 只在"有虚函数的类"里出现。你 01 里写的 `Matrix`（无虚函数）对象里**没有** vptr，成员从 offset 0 开始排——这就是为什么 01 的 demo 里 `rows_` 在 offset 0。

## 2. vptr 与 vtable 的结构（Itanium ABI，GCC/Clang 用；MSVC 类似）

```
内存（只读区 .rodata）               堆/栈上的对象
┌─────────────────────┐            ┌──────────────┐
│  Circle 的 vtable：    │            │ Circle 对象    │
│  [-16] offset-to-top  │            ├──────────────┤
│  [-8]  typeinfo 指针   │◄─RTTI──   │  vptr ────────┼──► 指向 vtable[0]
│  [0]   &Circle::draw  │◄───────────┤  (隐藏,offset0)│
│  [8]   &Circle::area  │            ├──────────────┤
│  [16]  &Circle::~Circle│           │  data 成员...  │
└─────────────────────┘            └──────────────┘
```

- **vtable**：每个类一张，是**函数指针数组**（前面还有 RTTI 元信息）。**全类共享一张**，所有该类的对象共用。
- **vptr**：每个对象一个，在对象**开头**（offset 0），指向本类 vtable 的函数区。
- **槽位下标编译期固定**：`draw` 恒在槽 0、`area` 恒在槽 1。**派生类覆盖 `draw` 时，是"把同一槽位里的函数指针换成自己的"**——这和你 Cool 编译器里"重写沿用父类下标、新方法追加新下标"是**逐字对应**的（见 §8）。

> **▶ 动手验证（强烈建议）**：用 g++ 直接导出真实虚表，亲眼核对上面的图。命令：
> ```bat
> g++ -std=c++17 -fdump-lang-class your.cpp -o app
> :: 会生成 your.cpp.001l.class，内容是每个类的 Vtable + 对象布局
> ```
> 以 `struct Base{virtual void f();virtual void g();int b;}; struct Der:Base{void f()override;virtual void h();int d;};` 为例，导出结果是（已实测，g++ 15.2）：
> ```
> Vtable for Der: 5 entries
> 0    (int (*)(...))0           ← offset-to-top
> 8    (int (*)(...))(&_ZTI3Der) ← typeinfo（RTTI）
> 16   (int (*)(...))Der::f      ← 虚函数槽 0（覆盖 Base::f）
> 24   (int (*)(...))Base::g     ← 槽 1（未覆盖，沿用 Base::g）
> 32   (int (*)(...))Der::h      ← 槽 2（新增）
> Class Der: size=16 align=8
>     vptr=((&Der::_ZTV3Der)+16)  ← vptr 指向 vtable 第 16 字节（跳过前两项元信息）
>     Base (primary-for Der) 0     ← 基类子对象在 offset 0（单继承零调整）
> ```
> 注意三点：① vptr 指向 `vtable + 16`（前 8 字节是 offset-to-top、再 8 字节是 typeinfo）；② 覆盖的 `f` 在槽 0、未覆盖的 `g` 沿用基类、新增的 `h` 追加——正是 §8 对照的"沿用/追加"；③ `size=16 align=8` 里 size 是补齐到对齐后的 16，而真实数据是 12（vptr 8 + int 4）。**这个工具让你从此不再"背"对象模型，而是"查"对象模型。**

## 3. 一次虚调用到底发生了什么（逐指令）

`Shape* p = new Circle; p->draw();` 编译后（伪汇编）：

```
mov  rax, [p]          ; ① 取 p 的 vptr（对象开头 8 字节）
mov  rdx, [rax + 0]    ; ② vtable[槽0] = &Circle::draw（draw 的槽位编译期已知）
call rdx               ; ③ 间接跳转
```

对比**非虚调用**（直接函数调用）：
```
call Shape::draw       ; 编译期就定死，一步到位
```

**成本分析**：虚调用 = 两次额外内存读取 + 一次间接跳转。真正的性能杀手不是这两条 `mov`，而是：

1. **阻止内联**：编译器看不到跳去哪，没法把函数体内联进来（内联是很多优化的前提）。
2. **分支预测/指令缓存**：间接跳转目标不固定，CPU 分支预测器容易猜错；vtable 和函数体分散在不同内存，易 I-cache miss。

> 这就是为什么 HPC 热点循环里，用虚函数（哪怕每对象只多 8 字节）可能让速度差好几倍；也是为什么模板/静态分发（`10`/`14`）在高性能库里更受青睐。**"多态很贵"的准确说法是"虚调用在热点路径很贵"**，普通业务代码里这点开销无感。

## 4. 单继承的对象布局（为什么能安全地把派生类当基类用）

```
class Base   { virtual void f(); int b_; };
class Derived: public Base { virtual void f() override; int d_; };

Derived 对象:
┌──────────────┐ offset 0
│    vptr       │ ──► Derived 的 vtable（f 槽指向 Derived::f）
├──────────────┤ offset 8
│   b_ (Base)   │   ← 基类子对象
├──────────────┤ offset 16
│   d_ (Derived)│   ← 派生类新增
└──────────────┘
```

**关键点**：**基类子对象在对象最前面（offset 0 起）**。所以：

- `Base* p = &derived;` **不需要调整指针**——`p` 就指向对象开头，`p->b_` 用编译期固定的偏移 8，在 `Derived` 对象里依然正确（这就是 04 里说的"继承属性保持原偏移"）。
- `Derived` 覆盖 `f` 时，只是把 vtable 槽 0 的函数指针从 `&Base::f` 换成 `&Derived::f`，对象布局和槽位下标都**不变**。

> 这和你 Cool 编译器里「继承的属性保持原偏移、重写的方法沿用父类下标」是**同一个内存原理**——因为这样"把派生类对象当基类用"时，所有偏移/下标都不用改，多态才成立。

## 5. 多重继承（Multiple Inheritance）：不止一个 vptr

```cpp
class A { virtual void fa(); int a_; };
class B { virtual void fb(); int b_; };
class C : public A, public B { void fa() override; void fb() override; int c_; };

C 对象:
┌──────────────┐ offset 0
│  vptr(A)      │ ──► C 的 A-vtable
├──────────────┤
│  a_           │
├──────────────┤
│  vptr(B)      │ ──► C 的 B-vtable   ← 第二个 vptr！
├──────────────┤
│  b_           │
├──────────────┤
│  c_           │
└──────────────┘
```

**为什么要有第二个 vptr**：`B* pb = &c;` 时，`pb` 必须指向 `B` 子对象（在 offset 16，不是 0！），编译器会**自动调整 this 指针**（`pb = (B*)((char*)&c + 16)`）。而 `B` 的方法需要看到"B 视角的 vtable"（`fb` 槽位），所以 `B` 子对象也带一个 vptr。

**this 调整 + thunk**：当 `C` 覆盖 `B::fb` 时，`fb` 的实现里 `this` 应该指向 `C` 对象开头，但通过 `pb->fb()` 调用时 `this` 传进来的是"B 子对象地址"（offset 16）。编译器在 vtable 里塞一个**thunk（跳板）**：先把 `this` 减回 16、再跳到真正的 `C::fb`。

> 你的 Cool 编译器可能没做多重继承（Cool 是单继承），但**你学 C++ 做深度学习编译器/系统底层时，LLVM/Clang 自己就是多重继承 + thunk 的典型**。这个机制是理解 C++ 源码和 ABI 的硬通货。

## 6. 虚继承（Virtual Inheritance）：菱形问题

```cpp
class Base   { int id_; };
class L : virtual public Base { ... };   // 虚继承
class R : virtual public Base { ... };
class D : public L, public R { ... };    // D 里只有一份 Base！
```

非虚继承时，`D` 里会有**两份** `Base`（`L` 一份、`R` 一份），访问 `id_` 会二义。`virtual` 继承让所有路径**共享同一个** `Base` 子对象。实现上，对象里会额外存一个 **vbase 指针**（指向虚基类子对象的位置），访问虚基类成员要走一次间接寻址。

> **实践建议**：虚继承又贵又复杂（额外指针 + 间接访问），**能不用就不用**。绝大多数菱形问题可以用"接口（纯虚抽象类）+ 组合"避开。知道它存在、能在报错时认出来即可，不必死磕实现细节。

## 7. RTTI：typeid 与 dynamic_cast 也住在 vtable 里

```cpp
Shape* p = new Circle;
typeid(*p).name();                  // "Circle"（多态对象，运行时类型）
dynamic_cast<Circle*>(p);           // 成功返回非空；若 p 不是 Circle 则返回 nullptr
```

- 这两个都要求类型是**多态的**（至少一个虚函数），因为它们靠 vtable 里藏的 **typeinfo 指针**（§2 的 `[-8]`）来识别运行时类型。
- `dynamic_cast` 是"安全向下转型"：运行时查 vtable 的 typeinfo，类型对得上就调整指针返回，对不上返回 `nullptr`（指针版）或抛 `bad_cast`（引用版）。**有开销**，别在热点用。

## 8. 与你 Cool 编译器的精确对照（本篇真正的价值）★

你已经在 `projects/coolc/src/codegen.cpp` 里亲手实现了分发表。把两边并排看：

| | 你的 Cool 编译器 | C++（Itanium ABI） |
|---|---|---|
| 对象头部存什么 | `tag`（指向 class_meta） | `vptr`（直接指向 vtable） |
| 方法表 | vtable（全局函数指针数组） | vtable（全局函数指针数组 + RTTI） |
| 覆盖方法 | 沿用父类下标、换函数指针 | 沿用槽位、换函数指针 |
| 新方法 | 追加新下标 | 追加新槽位 |
| 动态分派 | `tag → class_meta → vtable → fn`（**三跳**） | `vptr → vtable → fn`（**两跳**） |
| 静态分派 | `e@T.f` 直接 `call T.f` | 非虚函数直接 `call` |
| 对象存放 | 全在堆（`cool_alloc`，一切皆 `i8*`） | **值语义**：可栈上、可堆上、可内嵌成员 |
| 基本类型 | 装箱（Int/Bool 也是对象） | **不装箱**（`int` 就是 4 字节裸值） |

**两个最重要的差异（也是 C++ 快的原因）**：

1. **C++ 少一跳**：你的 Cool 里 `tag` 指向 class_meta，class_meta 里才存 vtable 指针（因为 class_meta 还要放类名/大小/类 ID 供 `case` 和 `type_name` 用）；C++ 的 vptr 直接指向 vtable，省掉中间那跳。
2. **C++ 值语义 + 不装箱**：Cool 里 `Int` 是堆上 16 字节对象、每次算术要拆箱装箱；C++ 的 `int` 是寄存器里 4 字节裸值。**这就是为什么 C++ 比"一切皆对象"的语言快一个量级**——`17` 会带你用这个视角重新审视你的 codegen，理解"装箱"这个设计决策的代价。

> 一句话：**你正在写的 Cool 编译器，就是在用 C++ 重新实现 C++ 的多态机制的一个"教学简化版"。** 学完 C++ 对象模型，你回头看自己的 codegen 会豁然开朗。

## 9. 易错点

1. **误以为对象里存了"函数"**：对象里只存 vptr（指针），函数体在代码区（Text），vtable 里存的是"函数地址"。
2. **把 `sizeof` 想当然**：多态对象比"成员之和"多 8 字节（vptr），且可能有**对齐填充**——`sizeof` 不一定等于成员大小之和（`14` 详讲对齐）。
3. **基类子对象在 offset 0**：这是单继承能"零开销把派生类当基类用"的根因；破坏它（多继承下）才需要 this 调整。
4. **用 `reinterpret_cast` 猜 vptr 位置**：vptr 的确切布局是 ABI 实现细节（Itanium vs MSVC 不同），别在可移植代码里硬编码；要理解机制，用 demo 里"手搓 vtable"的方式，而不是去读真实 vptr。
5. **在构造函数里调虚函数**：构造期间 vptr 还指向**当前类**的 vtable（派生类部分没建好），虚调用不会分发到派生类（`05` 已提，这里有了底层解释：vptr 是逐步"升级"的）。
6. **`dynamic_cast` 当免费工具用**：它有 RTTI 查表开销，热路径避免。
