## 精炼段

设计模式（GoF）是"反复出现的结构问题的成熟解法"，本质是把**多态**（05/06）用到真实代码里。四个最常用的：**策略模式**（可替换的算法/行为）、**观察者模式**（一对多的通知）、**工厂模式**（把"创建谁"延迟/集中）、**单例模式**（全局唯一实例）。但**现代 C++ 对很多模式做了"降维打击"**：策略模式 = 一个 `std::function` 或 lambda、命令模式 = 类型擦除、桥接 = PIMPL——语言特性直接吸收掉了模式的样板代码。**关键认识：模式是"手段"不是"目的"，理解了多态和类型擦除，模式就是自然结果，不必死记 23 个。**

---

## 0. 一句话直觉

> 设计模式就像"装修的经典户型"：卧室怎么摆、厨房怎么连，前人总结了成熟套路。但 C++ 装修师傅手里有更趁手的工具（lambda、模板、类型擦除），很多"经典户型"现在几行代码就搞定。**别把模式当教条背，要看到它背后的"多态 + 解耦"本质。**

## 1. 策略模式（Strategy）：可替换的行为

**问题**：同一个操作，想换不同算法（如排序用快排还是归并；算子的激活函数用 relu 还是 gelu）。

**经典写法（虚函数）**：
```cpp
class SortStrategy {
public:
    virtual ~SortStrategy() = default;
    virtual void sort(std::vector<int>& v) const = 0;
};
class QuickSort : public SortStrategy {
public:
    void sort(std::vector<int>& v) const override { /* 快排 */ }
};
void client(std::vector<int>& v, const SortStrategy& s) { s.sort(v); }
```

**现代 C++ 写法（lambda / 函数对象，零样板）**：
```cpp
void client(std::vector<int>& v, const std::function<void(std::vector<int>&)>& sort) {
    sort(v);
}
client(v, [](auto& x){ std::sort(x.begin(), x.end()); });   // 直接传行为
```
> **现代视角**：策略模式的本质是"把行为当参数传"。C++ 里 lambda 就是一等公民的行为，`std::function`（类型擦除）或模板（零开销）都能承载它——**不需要为每个策略写一个类**。这直接呼应你的 capstone 项目（算子分派器 = 策略模式的工程化）。

## 2. 观察者模式（Observer）：一对多通知

**问题**：一个对象状态变了，多个对象要跟着更新（如 UI、事件、pub-sub）。

```cpp
#include <functional>
#include <vector>

class Subject {
public:
    using Callback = std::function<void(int)>;   // 观察者 = 一个回调
    void subscribe(Callback cb) { observers_.push_back(std::move(cb)); }
    void notify(int value) { for (auto& cb : observers_) cb(value); }
private:
    std::vector<Callback> observers_;
};
```
> **现代视角**：观察者 = "回调列表"。经典 GoF 要定义 `Observer` 接口 + `ConcreteObserver`，现代 C++ 一个 `vector<std::function>` 就够。你在 CUDA/引擎里"注册回调"就是这个模式。

## 3. 工厂模式（Factory）：集中"创建谁"

**问题**：根据运行时信息（字符串/配置）创建不同子类对象，且不想把"创建逻辑"散落各处。

```cpp
#include <memory>
#include <unordered_map>
#include <functional>

class Shape { /* 05 的抽象类 */ };
class Circle : public Shape { /* ... */ };
class Square : public Shape { /* ... */ };

// 工厂：名字 → 创建函数（类型擦除 + 多态）
std::unordered_map<std::string, std::function<std::unique_ptr<Shape>()>> factory = {
    {"circle", []{ return std::make_unique<Circle>(); }},
    {"square", []{ return std::make_unique<Square>(); }},
};
auto s = factory["circle"]();   // 按名字造对象
```
> **现代视角**：工厂 = "名字/参数 → 创建函数的映射表"。你的 capstone（算子分派器）就是"工厂 + 策略"的合体：按名字创建/查找算子并执行。

## 4. 单例模式（Singleton）：全局唯一实例

**问题**：某个对象全程序只该有一个（如配置、日志、设备管理器）。

**现代 C++ 正确写法（Meyers Singleton，线程安全、零手动）**：
```cpp
class Logger {
public:
    static Logger& instance() {          // 函数内静态变量：C++11 起线程安全
        static Logger inst;              // 第一次调用时构造，程序结束自动析构
        return inst;
    }
    void log(const std::string& msg) { /* ... */ }
private:
    Logger() = default;                  // 私有构造，禁止外部 new
    Logger(const Logger&) = delete;      // 禁止拷贝
};
// 用法：Logger::instance().log("hi");
```
- **为什么函数内 static**：C++11 保证其初始化**线程安全**（只构造一次），且**延迟初始化**（用到才构造）、**自动析构**（RAII）。
- **警示**：单例是"全局可变状态"，**别滥用**——它让代码难测试、隐式耦合。现代实践倾向**依赖注入**（把对象传进去）而非全局单例。

## 5. PIMPL：隐藏实现 + 保持 ABI 稳定

**问题**：头文件暴露了所有私有成员，改实现就要重新编译所有 include 者（`13`/`18` 的 ABI 问题）。

**PIMPL（Pointer to IMPLementation）**：把实现藏到"指针指向的类"里：
```cpp
// widget.h —— 只暴露指针，不暴露实现细节
class Widget {
public:
    Widget();
    ~Widget();                 // 必须显式声明（见下）
    void draw();
private:
    struct Impl;               // 只前置声明，不定义
    std::unique_ptr<Impl> pImpl_;   // 指向真正的实现
};

// widget.cpp —— 实现细节全在这，改它不触发 include 者重编
struct Widget::Impl { int data_; /* 大量私有成员 */ };
Widget::Widget() : pImpl_(std::make_unique<Impl>()) {}
Widget::~Widget() = default;    // 析构必须在这里定义（Impl 完整类型才可见）
void Widget::draw() { /* pImpl_->... */ }
```
- **收益**：改私有实现，调用者**不用重编**（ABI 稳定）；编译更快（头文件变小）。
- **代价**：多一次指针间接 + 一次堆分配。这是很多库（Qt、大量商业库）的标配。

## 6. 类型擦除（Type Erasure）：虚函数 + 模板的桥

**这是现代 C++ 最重要的"模式"**，也是你 capstone 的核心：

> 类型擦除 = 用"虚函数"提供**统一接口**，用"模板"包装**任意具体类型**，从而把"不同类型"塞进"同一容器/接口"。

```cpp
// 任何"能 Ret(Arg) 调用"的东西（函数/函数对象/lambda）都能装进 Function
template<class Ret, class Arg>
class Function {
    struct Concept { virtual Ret call(Arg) const = 0; virtual ~Concept() = default; };
    template<class F>
    struct Model : Concept { F f; Ret call(Arg a) const override { return f(a); } };
    std::unique_ptr<Concept> impl_;
public:
    template<class F> Function(F f) : impl_(std::make_unique<Model<F>>(std::move(f))) {}
    Ret operator()(Arg a) const { return impl_->call(a); }
};
```
- 这就是 `std::function` 的原理（简化版）。
- **它同时用了**：虚函数（`Concept` 的 vtable，`06`）、模板（`Model<F>`，`10`）、RAII（`unique_ptr`，`07`）、移动语义（`08`）。
- **价值**：把"编译期多态（模板）"和"运行期多态（虚函数）"桥接起来——既能存异构类型，又保留类型安全。**你的 capstone 算子分派器就是它，也是 TVM/vLLM 等深度学习编译器算子注册的核心手法。**

## 7. 现代 C++ 对模式的"降维打击"（总结）

| 经典模式 | 现代 C++ 的替代 |
|---|---|
| 策略模式 | lambda / `std::function` |
| 命令模式 | lambda / `std::function` |
| 观察者模式 | `vector<std::function>` |
| 工厂模式 | `map<string, std::function<...>>` |
| 单例模式 | Meyers 单例（函数内 static） |
| 桥接模式 / 隐藏实现 | PIMPL + type erasure |

> **核心结论**：GoF 的 23 个模式里，很多在 C++ 里已经"退化"成语言特性 + STL 的常规用法。**你真正要掌握的不是模式清单，而是三个底层能力：多态（虚函数）、泛型（模板）、类型擦除（两者的桥）**——这三样学透了，模式信手拈来。

## 8. 易错点

1. **把模式当教条硬套**：为了"用上模式"而加一层抽象，代码反而更复杂。**先有实际问题，再选模式。**
2. **滥用单例**：全局可变状态难测试、隐式耦合。优先依赖注入。
3. **PIMPL 忘了在 .cpp 里定义析构**：`unique_ptr<Impl>` 的析构需要 `Impl` 完整类型，若在头文件里 `= default` 会编译错（incomplete type）。
4. **类型擦除的虚函数调用开销**：`std::function`/type erasure 的调用是虚分派（`06` 的开销），热点路径用模板（零开销）而非 `std::function`。
5. **观察者没管理生命周期**：subject 持有回调，回调里引用已销毁的对象 → 悬空。用 `weak_ptr`（`07`）或明确取消订阅。

## 9. 自测题

1. **概念题**：类型擦除是如何"桥接"编译期多态（模板）和运行期多态（虚函数）的？它解决了什么问题？
2. **应用题**：用类型擦除实现一个"可存任意一元函数"的 `AnyUnary`，并把三个不同类型的可调用对象（函数指针、带状态的函数对象、捕获变量的 lambda）都装进一个 `vector<AnyUnary>` 里统一调用。
3. **思考题**：为什么 `std::function` 不适合放在"千万次调用的热点循环"里？如果热点路径需要"可替换的行为"，应该用什么替代？（提示：`06` 的虚调用开销 vs `10` 的模板零开销）
