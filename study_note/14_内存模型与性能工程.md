## 精炼段

现代 CPU 的性能瓶颈通常不在"算"，而在"**搬**"——从内存把数据搬到寄存器。所以 C++ 性能工程的第一性原理是**数据布局与缓存友好**：对象成员的对齐与 padding 决定 `sizeof` 和缓存行占用；**AoS（结构体数组）vs SoA（数组结构体）**的选择决定热点循环的访存模式；**false sharing**（多线程写同一缓存行的不同变量）会让并行性能暴跌。`move` 优于 `copy`、模板优于虚函数（可内联）、内存池优于 `malloc`，都是从不同侧面压缩"搬"的开销。**你在 CUDA 里学的合并访存、shared memory、内存层级，是同一套东西在 CPU 上的投影。**

---

## 0. 一句话直觉

> 你 CUDA 里已经刻进肌肉记忆：**算术强度低 = memory-bound，优化方向是"少搬、搬得整齐"**。CPU 上一模一样。C++ 性能工程的核心不是"写更快的算法"，而是**让数据在内存里摆得让 CPU 少跑腿**：连续的数据能一次预取一整条缓存行，离散的数据每次都要去主存现取。所以"改布局"常常比"改算法"更赚——这正是你从 GPU 优化能无缝迁移过来的直觉。

## 1. 对象布局：对齐与 padding（`sizeof` 不等于成员之和）

```cpp
struct A { char c; int i; };        // sizeof(A) = ?
struct B { int i; char c; };        // sizeof(B) = ?
```
答案：**A 是 8，B 是 8**（不是 5！）。因为 `int` 要求 4 字节对齐，`char c` 后面要**填充 3 字节 padding** 才能让 `i` 对齐：

```
A: [c][pad][pad][pad][ i ][ i ][ i ][ i ]   → 8 字节
B: [ i ][ i ][ i ][ i ][c][pad][pad][pad]   → 8 字节（尾部也填充到 4 的倍数）
```

**规则**：成员按声明顺序排布，每个成员要对齐到自己的对齐要求；结构体整体大小对齐到最大成员的对齐值。**对齐是为了让 CPU 一次 load 指令能读出整个 int**（不对齐可能跨越缓存行、甚至某些架构直接崩溃）。

**优化技巧——重排成员省内存**：
```cpp
struct Bad  { char a; int b; char c; int d; };   // 4+4+4+4 = 16（每个 int 前都有 padding）
struct Good { int b; int d; char a; char c; };   // 4+4+1+1 = 12（大的在前，小的挤一起）
```
> 大多数时候不用手动重排（编译器不自动重排是为了保持 ABI 稳定）；但**热数据、要进缓存/显存的大数组**，布局值得精心设计。

## 2. 缓存行与 false sharing（多线程性能杀手）

**缓存行（cache line）= 64 字节**：CPU 从内存取数据的最小单位，一次搬 64 字节。

**False sharing（伪共享）**：两个线程各写**不同变量**，但它们落在**同一缓存行**里 → 缓存一致性协议让它们互相"打架"，并行性能暴跌：

```cpp
struct Counter {           // 两个线程各 ++ 一个字段
    int a;                 // 但 a、b 在同一缓存行里！
    int b;                 // 线程1写 a、线程2写 b，却要互相失效缓存行
};
```
**解法：把热点变量隔开到不同缓存行**（让 a、b 各自独占一个缓存行）：
```cpp
struct Counter {
    alignas(64) int a;   // a 对齐到 64 字节边界，独占第 0 个缓存行
    alignas(64) int b;   // b 对齐到 64 字节边界，独占第 1 个缓存行
};                       // sizeof(Counter) ≈ 128：两个 int 各占一行 + padding
// 线程1 写 a、线程2 写 b → 落在不同缓存行，缓存一致性不再互相失效
```
> 更通用的做法：整个结构体 `alignas(64)`，或用 `<new>` 里的 `std::hardware_destructive_interference_size`（C++17，编译器给出的"避免伪共享"推荐对齐值）。
> 这是**并发性能优化最隐蔽也最常见**的坑：加了锁/原子却还是慢，先查是不是 false sharing。

## 3. AoS vs SoA（HPC 最重要的布局选择）★

**AoS（Array of Structs，结构体数组）** vs **SoA（Struct of Arrays，数组结构体）**，是决定热点循环性能的布局选择：

```cpp
// AoS：每个粒子一个结构体，数组存结构体
struct Particle { float x, y, z, vx, vy, vz; };
std::vector<Particle> particles_aos(1'000'000);

// SoA：每种属性一个数组
struct Particles {
    std::vector<float> x, y, z, vx, vy, vz;   // 每个各 1'000'000 个
};
```

**关键区别——热点循环只访问 `x` 时的访存模式**：
```
AoS: [x y z vx vy vz][x y z vx vy vz][x y z vx vy vz]...
     ▲ 访问 x 要跳着读：每 6 个 float 只用一个 → 缓存利用率 1/6

SoA: [x x x x x x ...][y y y y ...][z z z ...]...
     ▲ 访问 x 连续读：整条缓存行全是 x → 缓存利用率 100%
```

**结论**：
- **只访问少数几个字段**（如物理模拟每步只更新 `vx`）→ **SoA 完胜**（连续访存，SIMD 友好）。
- **访问每个对象的全部字段**（如"移动整个粒子"）→ AoS 也可（都在一个缓存行）。
- **你 CUDA 的合并访存就是 SoA 思想**：线程 0..31 读连续的地址，一条指令搬满 128 字节。CPU 的 SIMD（`std::simd`、编译器自动向量化）吃的是同一套"连续 + 对齐"。

## 4. move 优于 copy、模板优于虚函数（性能视角回看）

| 优化 | 原理 | 收益 |
|---|---|---|
| `std::move` 大对象 | 只改指针，不复制整块内存（08） | 省 O(n) 拷贝 |
| `emplace_back` | 原地构造，省临时对象 | 省一次构造+移动 |
| 模板（编译期多态） | 可内联、无虚表跳转（10） | 热点循环可差数倍 |
| `reserve` 预分配 | 避免 vector 反复扩容拷贝 | 省多次分配+搬移 |
| 内存池分配器 | 免去 malloc 的锁竞争与碎片（12） | 高频小对象快一个量级 |

**虚函数 vs 模板的量化**：虚函数调用多一次间接跳转 + 无法内联；若在千万次循环里，多态每个对象的 `draw()` 都要查表，模板则在编译期展开成直接调用（甚至被内联、向量化）。**但虚函数的"去虚化（devirtualization）"**：若编译器能确定动态类型（如 `final` 类、局部对象），会优化掉虚表跳转——所以别为"可能慢"过度设计，先 profile（`15`）。

## 5. 性能工程的方法论（先测量，再优化）

```
① Profile 找到热点 → ② 判断 bound（compute/memory/latency）→ ③ 选对优化 → ④ 再测量验证
```

- **永远先 profile**（`gprof`/`perf`/`valgrind --tool=callgrind`），别靠猜。你 CUDA 里"先算算术强度、判 bound"的纪律，CPU 上同样适用（Roofline 模型原样搬来）。
- **Amdahl 教训**：优化只占 1% 运行时的部分，最多快 1%。先优化"占总时间最多的部分"。
- **诚实测量**：优化后必须重测，防止"感觉快了"的错觉（编译器可能已经替你优化了）。

## 6. 图示：为什么 SoA 让 SIMD 高效

```
AoS 访问 x（跨步访存，缓存利用率低）：
  [x y z][x y z][x y z][x y z]
   ▲    ▲    ▲    ▲      ← 每次 load 128 字节缓存行，只用 1/3

SoA 访问 x（连续访存，满缓存行 + SIMD 一次算 4/8 个）：
  [x x x x x x x x][x x x x x x x x]
   ▲───────────────▲ ← SIMD 一条指令算 8 个 x，整条缓存行全用上
```

## 7. 易错点

1. **过度优化**：没 profile 就"优化"，往往白干甚至变慢（破坏可读性、阻碍编译器优化）。
2. **AoS/SoA 选反**：热点循环只碰一个字段却用 AoS，缓存利用率崩到 1/N。
3. **false sharing 不自知**：多线程写了同一缓存行的变量，性能莫名差。
4. **`sizeof` 想当然**：有 padding，`sizeof` ≠ 成员和。热数据大数组要算清楚。
5. **对齐被破坏**：`reinterpret_cast` 到不满足对齐的类型、`#pragma pack` 乱用 → 未定义行为。
6. **虚函数滥用**：在热点路径用多态当"方便"，没想过用模板/静态分发。

## 8. 自测题

1. **概念题**：AoS 和 SoA 的区别是什么？为什么"只访问一个字段"的热点循环里 SoA 远优于 AoS？
2. **应用题**：写两版"更新 N 个粒子的 x 坐标（x += vx*dt）"的循环——AoS 版和 SoA 版——并解释为什么 SoA 版对编译器的 SIMD 向量化更友好（可以加 `-O2 -ftree-vectorize` 看效果）。
3. **思考题**：false sharing 为什么会让"两个线程各写一个独立 int"变慢？它和你 CUDA 里的什么现象是同源的？（提示：缓存一致性协议 vs GPU 的 warp divergence/合并访存）
