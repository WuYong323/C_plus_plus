## 精炼段

C++11 起，多线程是**语言标准**的一部分（不再靠 pthread 等平台 API）。核心四件套：**`std::thread`** 创建线程（`join` 等待 / `detach` 分离）、**`std::mutex` + 锁** 保护共享数据（`lock_guard`/`scoped_lock` 让锁也 RAII）、**`std::condition_variable`** 做线程间等待/唤醒（生产者-消费者）、**`std::async`/`std::future`** 异步拿结果。铁律不变：**数据竞争（data race）= 未定义行为**（`18`），所以要么用锁、要么用 atomic。你在 CUDA 里学的"多线程写同一地址会丢更新、要同步"在这里**一字不差**——只是同步原语从 `__syncthreads`/`atomicAdd` 换成了 `mutex`/`atomic`。

---

## 0. 一句话直觉

> 单线程是"一个人干所有活"，多线程是"几个工人共享一个车间"。工人并行干活快，但**共享的工具（数据）不能同时被两个人抢**——得靠"锁"（一次只能一个人用）和"约定"（原子操作）协调。你 CUDA 里 `__syncthreads()` 是"block 内工人对齐"，C++ 的 `mutex`/`atomic` 是"CPU 线程间协调"——**同一套"多执行单元 + 共享数据"的问题，两种语法**。

## 1. std::thread：创建与收尾

```cpp
#include <thread>
#include <iostream>

void work(int id) { std::cout << "thread " << id << "\n"; }

int main() {
    std::thread t1(work, 1);       // 创建线程，传参
    std::thread t2(work, 2);
    t1.join();                     // 等待 t1 结束（阻塞）
    t2.join();                     // 等待 t2 结束
    // 若线程对象析构时还没 join 也没 detach → std::terminate！
}
```

| 操作 | 含义 | 注意 |
|---|---|---|
| `join()` | 阻塞等待线程结束 | 线程对象析构前必须 join 或 detach |
| `detach()` | 分离，线程独立运行 | 之后无法再 join，主线程可能先退出 |
| `std::jthread`（C++20） | 自动 join 的线程 | 析构时自动 join，**更安全，优先用** |

## 2. 数据竞争与互斥锁 mutex

多个线程同时写共享变量 → **data race = UB**（`18`）。解法之一：**互斥锁**，让"读-改-写"变成原子的一段（临界区）：

```cpp
#include <mutex>

std::mutex mtx;
int counter = 0;

void inc(int n) {
    for (int i = 0; i < n; ++i) {
        std::lock_guard<std::mutex> lock(mtx);   // 加锁（RAII！）
        ++counter;                                // 临界区：读-改-写
    }                                            // lock 析构自动解锁
}
```

**锁也要 RAII**（`07` 思想的延伸）：`std::lock_guard` 构造加锁、析构解锁——**任何 return/异常都不会漏解锁**。别手写 `mtx.lock()`/`mtx.unlock()`（中间抛异常就死锁）。

**多把锁**用 `std::scoped_lock`（C++17），按固定顺序加锁、避免死锁：
```cpp
std::scoped_lock lock(mtx1, mtx2);   // 一次性锁两把，且死锁安全（内部按序）
```

## 3. 条件变量 condition_variable（生产者-消费者）

线程 A 要"等某个条件成立"再干活，不是忙等（busy-wait 烧 CPU），而是**睡下，等别人唤醒**：

```cpp
#include <mutex>
#include <condition_variable>
#include <queue>

std::mutex mtx;
std::condition_variable cv;
std::queue<int> q;

// 生产者
void produce(int x) {
    { std::lock_guard lk(mtx); q.push(x); }
    cv.notify_one();                 // 唤醒一个等待者
}

// 消费者
int consume() {
    std::unique_lock lk(mtx);        // cv 需要 unique_lock（能手动 unlock/lock）
    cv.wait(lk, []{ return !q.empty(); });   // 睡下，直到 q 非空（且自动重新加锁）
    int x = q.front(); q.pop();
    return x;
}
```

**两个关键点**：
1. **`wait` 的谓词**（`!q.empty()`）：防"虚假唤醒"（spurious wakeup）——线程可能没被 notify 也醒来，必须**再检查一次条件**。
2. **为什么 cv 用 `unique_lock` 而非 `lock_guard`**：`wait` 内部要**先解锁、睡、醒来再重新加锁**，需要能手动 lock/unlock 的 `unique_lock`。

## 4. 异步 async / future / promise

"算一个东西，我先干别的，待会儿来拿结果"：

```cpp
#include <future>

int heavy(int x) { /* 耗时计算 */ return x * 2; }

std::future<int> fut = std::async(std::launch::async, heavy, 21);  // 异步跑
// ... 主线程干别的 ...
int result = fut.get();   // 阻塞等待结果（只能 get 一次）
```

- **`std::async`**：启动异步任务，返回 `std::future`。
- **`std::future`**：结果的"占位符"，`get()` 阻塞取结果。
- **`std::promise`**：手动在某个时刻 set 值，配 `future` 做更灵活的控制。

> **取舍**：`async` 简单，但底层是"线程池还是新线程"由实现决定，且任务粒度粗时线程创建开销大。**CPU 密集的细粒度并行，通常用线程池 + 任务队列**（工业里常见，如 TBB/线程池），`async` 适合"几路大任务"。

## 5. atomic 回顾（衔接 18）

锁能保护任何临界区，但**只保护一个变量**时，`std::atomic` 更轻（无锁、不阻塞）：

```cpp
std::atomic<int> counter{0};
void inc(int n) { for (int i=0;i<n;++i) counter.fetch_add(1); }   // 原子加，无需锁
```
- 锁 = 保护**一段代码**（临界区）；atomic = 保护**一个值**的操作。
- 内存序（`relaxed`/`acquire`/`release`/`seq_cst`）见 `18`——先 `seq_cst` 写对，再降级。

## 6. 线程安全与 false sharing（衔接 14）

- **线程安全（thread-safe）**：多个线程同时调用也正确的类/函数。不是所有类都线程安全（STL 容器**不是**线程安全的，要自己加锁）。
- **false sharing**：多线程各写不同变量但落在同一缓存行 → 互相失效（`14` 已讲 + 已给出 `alignas(64)` 解法）。

## 7. 与 CUDA 的对照（你的经验直接迁移）

| CPU 多线程（C++） | GPU（你的 CUDA 经验） | 同源思想 |
|---|---|---|
| `std::thread` | block / thread | 并行执行单元 |
| `std::mutex` | `__syncthreads()`（block 内对齐） | 同步 |
| `std::atomic` | `atomicAdd` / `__threadfence` | 原子操作与内存序 |
| data race = UB | 写冲突 = 不确定结果 | 数据竞争 |
| false sharing | bank conflict / 合并访存 | 缓存/访存布局 |

> **一句话**：你 CUDA 里养成的"先想数据竞争、再想同步、最后想访存布局"的肌肉记忆，写 CPU 多线程时**原样复用**——只是 API 名不同。

## 8. 易错点

1. **线程对象析构前没 join/detach** → `std::terminate`。用 `std::jthread` 自动 join。
2. **data race 用 `volatile` 同步** → UB（`18` 已讲，volatile≠atomic）。
3. **锁没 RAII**：手写 `lock()/unlock()`，中途抛异常 → 死锁。用 `lock_guard`/`scoped_lock`。
4. **条件变量漏谓词**：`wait` 不带谓词，虚假唤醒后继续执行 → 读空队列崩溃。
5. **锁的粒度**：锁太大 → 串行化、性能差；锁太小 → 保护不住。**先正确（大锁），再优化（缩小/换 atomic）。**
6. **STL 容器当线程安全用**：`vector`/`map` 多线程无锁访问是 UB，要自己加锁或用无锁结构。
