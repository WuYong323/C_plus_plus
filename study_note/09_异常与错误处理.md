## 精炼段

异常是一种"错误信号沿调用栈向上传播、由最近的匹配 `catch` 接手"的机制——它把"出错"从"每层手动 return 错误码"里解放出来。异常的威力依赖 **RAII**：栈展开（stack unwinding）时，所有已构造对象的析构函数**保证**被调用，所以哪怕抛异常，资源也绝不泄漏。它有三个异常安全级别：**nothrow / basic / strong**（strong 靠 copy-and-swap 实现）。但异常有开销、且不适合热路径和"可预期、高频"的失败——现代 C++ 于是提供 `std::optional`（可能没有值）、`std::expected`（值或错误，C++23）和 `std::error_code` 作为**结构化**的替代，让"可能失败"写进类型。

---

## 0. 一句话直觉

> 竞赛里你写深递归/深调用，某层 `dfs` 发现无解，得一层层 `return -1` 把失败传回去，中间每层都要写 `if (ret == -1) return -1`——又啰嗦又容易漏。异常就是一条"**逃生通道**"：深处直接 `throw`，一路穿过所有中间层（中间层什么都不用写），直达最外层准备好的 `catch`。而 RAII 保证：这条逃生通道上，所有局部资源的"遗嘱"（析构）都会被执行——**跑路也不忘善后**。

## 1. try / throw / catch 的基本机制

```cpp
#include <stdexcept>
#include <iostream>

int safe_div(int a, int b) {
    if (b == 0) throw std::runtime_error("division by zero");   // 抛出异常
    return a / b;
}

int main() {
    try {
        std::cout << safe_div(10, 0) << "\n";    // 这里会 throw
        std::cout << "这行不会执行\n";
    } catch (const std::runtime_error& e) {      // 按 const 引用捕获（避免切片！）
        std::cout << "caught: " << e.what() << "\n";
    }
}
```

- **`throw`**：抛出一个异常对象（通常派生自 `std::exception`）。
- **`catch`**：按类型匹配，**从内到外**找第一个能匹配的 `catch`。
- **捕获方式**：**几乎总是 `const X&`**（按引用捕获）。按值捕获会切片（`04`），按非 const 引用捕获不必要。
- **标准异常层次**：`std::exception` 为基类，常见子类 `std::runtime_error`（运行时错误）、`std::logic_error`（逻辑错误）、`std::out_of_range`、`std::bad_alloc`（new 失败）等。

## 2. 栈展开 + RAII = 异常安全的基石

异常传播时，会**逐层销毁**调用栈上所有"已完整构造"的局部对象——这一步叫**栈展开（stack unwinding）**：

```cpp
void f() {
    std::vector<int> big(1'000'000);   // RAII 资源
    g();                               // g 抛异常
    // big 的析构一定被调用，内存一定释放 —— 不用你写任何清理代码
}
```
> 这就是 07 说的"RAII 天然异常安全"：析构由栈展开保证，**无论从哪一层 throw、从哪个分支 return**，资源都自动归还。裸 `new`/`delete` 做不到这一点（throw 会跳过你手写的 delete）。

## 3. 异常安全三级别（写健壮库的硬标准）

| 级别 | 承诺 | 实现 |
|---|---|---|
| **nothrow（不抛）** | 绝不出错、绝不抛 | 析构函数、移动、`swap`、释放内存——一律 `noexcept` |
| **basic（基本）** | 抛了也不泄漏、对象仍"有效"（但内容未定） | 用 RAII 管理资源 |
| **strong（强）** | 抛了就像没调用过，状态完全不变 | **copy-and-swap** 惯用法 |

**copy-and-swap**（实现 strong guarantee 的经典手法）：
```cpp
class Matrix {
public:
    Matrix& operator=(const Matrix& o) {   // 强异常安全的拷贝赋值
        Matrix tmp(o);                     // ① 先拷贝到临时（若这里 throw，this 未受影响）
        swap(tmp);                         // ② 与临时交换（swap 是 noexcept 的）
        return *this;                      // ③ tmp 析构时释放 this 的旧资源
    }
    void swap(Matrix& o) noexcept {        // swap 必须不抛
        std::swap(rows_, o.rows_); std::swap(cols_, o.cols_); std::swap(data_, o.data_);
    }
};
```
> 关键：**先做所有可能失败的操作（拷贝），再做不可能失败的操作（swap）**。这样中途抛异常时，原对象纹丝不动。

## 4. noexcept：把"不抛"写进类型

```cpp
void f() noexcept;          // 承诺：f 不抛异常（若真抛了 → std::terminate）
```
- **析构函数默认 noexcept**（除非成员析构会抛）；**移动构造/赋值、`swap` 应标 noexcept**（否则 `vector` 扩容退化到拷贝，见 08）。
- 作用：① 文档化契约；② 让编译器做优化（如 `vector` 扩容走移动）；③ 让调用者写异常安全代码时有依据。

## 5. 现代结构化错误处理：optional / expected / error_code

异常适合"**意外、罕见、无法就地处理**"的失败；但对"**可预期、常见、就地能处理**"的失败，用返回值更清晰高效：

### 5.1 std::optional（C++17）："可能有值，可能没有"

```cpp
#include <optional>
std::optional<int> find(const std::vector<int>& v, int target) {
    for (int x : v) if (x == target) return x;   // 找到：有值
    return std::nullopt;                         // 没找到：空
}
auto r = find(v, 7);
if (r) std::cout << "found " << *r;       // 有值用 *r
```

### 5.2 std::expected（C++23）："要么值，要么错误"

```cpp
// C++23：返回值带"错误"分支，错误是结构化的（比 optional 多了"为什么失败"）
// std::expected<int, std::error_code> parse(const std::string& s) {
//     if (ok) return value;
//     return std::unexpected(make_error_code(...));
// }
```
> 你的基线是 C++17，`std::expected` 属 C++23 亮点（`16` 会提）；C++17 里可用 `std::optional` 或库级 `tl::expected` 替代。

### 5.3 std::error_code / std::error_condition

系统调用（文件、网络、GPU 驱动）常用 `std::error_code` 承载平台错误码，配合 `std::system_error`。`std::filesystem`、`std::thread` 等都返回它。

## 6. 何时用异常 vs 错误码（工程决策）

| 场景 | 用 | 理由 |
|---|---|---|
| 罕见、意外、深层调用栈里的失败 | 异常 | 免去层层手动传递，RAII 保证清理 |
| 可预期、高频、需就地处理（解析失败、查找失败） | `optional`/`expected`/错误码 | 无异常开销，控制流显式 |
| 热路径 / 实时 / 内核 | 错误码 | 异常机制有运行时成本，且不可用于某些环境 |
| 资源管理（构造/析构） | RAII + 异常 | 二者是搭档 |

> **实践共识**：Google C++ Style 曾禁用异常（历史包袱 + 存量代码），现代许多团队用"异常处理罕见错误 + 返回值处理预期错误"的混合。**你的 infra/CUDA 代码里，显存分配失败（`cudaMalloc` 返回错误码）通常走错误码，而不是异常**——因为它是"可预期的资源不足"，且 GPU API 本身返回错误码。

## 7. 易错点

1. **按值捕获异常导致切片**：`catch (std::exception e)` 丢派生类信息。用 `catch (const std::exception& e)`。
2. **catch 顺序错误**：基类 `catch` 放在派生类 `catch` 前面，会"拦截"掉派生类异常。**先具体后一般。**
3. **析构函数里抛异常**：析构默认 noexcept，若在析构里 `throw` 会 `std::terminate`；且栈展开过程中再抛异常 = 双重异常 → 崩溃。**析构永远别抛。**
4. **在构造函数里泄漏**：构造中途 throw，之前 `new` 的成员还没交给 RAII 管 → 泄漏。用智能指针成员（构造失败它们自动析构）。
5. **吞异常**：`catch(...) {}` 空处理，把错误藏起来——debug 噩梦。要么处理，要么重新 `throw;`。
6. **用异常做普通控制流**：`throw` 当 `goto` 用，性能差且语义混乱。
7. **移动构造忘了 noexcept**：`vector` 扩容退化拷贝（08 的坑，这里补全了"为什么"：异常安全）。
